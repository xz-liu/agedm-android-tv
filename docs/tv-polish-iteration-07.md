# 0.3.4：恢复在线播放直接交给播放器加载

用户确认 0.3.3 中“只有已下载的能播放”，问题集中在在线路径。0.3.2 为避免下载 HTML/错误类型内容，在共享 `WebStreamResolver.resolve()` 中加入了强制 `verifyStream()`：解析到视频地址后，必须先由 OkHttp 发起另一次 GET 并通过检查，才允许 Media3 启动。离线播放绕过了这个步骤，因此不受影响。

这改变了普通播放的请求顺序：额外请求可能提前消耗一次性地址；单独的校验请求被拒绝、超时或无法连接时，也会提前否决播放器本来可以尝试的地址。现有测试没有覆盖从 WebView 解析结果交接到原生在线播放的完整路径。

## 修改

- 在线解析结果直接交给原播放器，不再发起额外的阻塞预检 GET。
- 内容校验明确命名为 `verifyDownloadStream()`，只在下载准备服务创建持久化下载任务之前调用，继续防止把网页误存成完整视频。
- 浏览器提供的 HLS 类型提示、原始播放地址和请求头照常传递。0.3.3 的下载清单修复、本地播放逻辑和共享历史记录保持原样。

## 回归验证

新增两项 Robolectric/MockWebServer 测试，实际调用 WebStreamResolver 的 JavaScript bridge 并等待其解析结果：

1. 模拟只允许读取一次的 HLS 清单。解析完成前不请求媒体；随后 Media3 经 HTTP 加载清单和 TS 分片，完成音视频轨道准备，总计两次请求。旧版在解析阶段就提前消费了媒体请求，测试失败；修复后通过。
2. 模拟无后缀 HLS，由浏览器传递 MIME。预检端点返回 410 时，旧版在播放器启动前抛异常；修复后无需额外 HTTP 请求即可交出原地址和类型。

全部 50 项测试、`lintDebug`、Debug/Release 构建通过。Release 为 0.3.4 / versionCode 9，签名与上一版一致，可覆盖安装保留数据。

这证实并修复了新增预检引入的在线路径回归，不代表已经取得用户电视的具体 HTTP/解码异常。没有连接电视，轨道准备测试也不能代替设备硬件解码实测。
